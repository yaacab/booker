# Проверка утечек секретов — Букер

Локальный gate: `python3 scripts/check_secret_exposure.py --source --deploy-payload`. Source mode берёт tracked и untracked проектные файлы через `git ls-files`, **не** читает `.git`, `outputs`/вложенные worktree, venv, `node_modules`, `.next` и пользовательские `data/uploads`. Deploy mode отдельно получает **фактический список rsync dry-run** с тем же [файлом исключений](../../infra/rsync-booker-excludes.txt), который использует `deploy-vps.sh`; он блокирует symlink, чувствительное имя, неизвестный бинарный файл и обнаруженный секрет. Локальные `.env*`, ключи, `outputs`, рабочие кэши и uploads не входят в payload. `deploy-vps.sh` запускает gate до отправки файлов. После свежей сборки web: `python3 scripts/check_secret_exposure.py --build`; проверяются `.next/static`, `.next/server`, `.next/standalone`, но не cache. Отсутствующий `BUILD_ID` — ошибка, а не пустой PASS. VPS deploy повторяет build scan **после своей сборки** с `--env-file /etc/booker/booker-api.env` до переключения web; при FAIL возвращает предыдущую `.next`. Для подготовленных локальных логов/артефактов разрешён `--artifact <path>` только внутри `logs`, `apps/api/test-results`, `apps/web/test-results` или `apps/web/playwright-report`; путь к пользовательским вложениям отвергается.

Сканер ищет ключи провайдеров, заголовки private key, URL БД с непустым паролем, имена `NEXT_PUBLIC_*SECRET/TOKEN/PASSWORD/API_KEY`, секретные значения в явных присваиваниях и буквальное появление настроенных `BOOKER_WEBHOOK_SECRET`, `BOOKER_PAYMENT_SECRET_KEY`, `BOOKER_EMAIL_API_KEY`, `BOOKER_SMS_API_KEY`, `BOOKER_OBJECT_STORAGE_SECRET_KEY`. В build mode с `--env-file` он также ищет фактические значения этих настроек и пароль/URL БД, не печатая их. Короткое значение (3–7 символов) ищется только как отдельный литерал в кавычках, чтобы не считать любое вхождение обычного слова утечкой. Placeholder, пустые значения и очевидные dev/example формы не являются найденным секретом. Файл больше 10 MiB даёт ошибку `oversized-unscanned`; в бинарных файлах source/build проверяются точные сигнатуры токенов/private key и настроенные canary без общего текстового разбора. Deploy mode дополнительно отвергает неизвестный бинарный формат и допускает только известные публичные медиа. Вывод содержит **только SHA-256 идентификатор пути, номер строки и тип правила**, никогда имя файла или найденное значение. При находке CI падает; значение смотреть и удалять в защищённой рабочей процедуре, не копировать в issue/лог.

Точный allowlist в `scripts/check_secret_exposure.py` содержит SHA-256 **конкретных синтетических токенов и локальных demo DB-паролей** только в перечисленных тестовых fixture, README/dev runbook и `migrate-postgres-docker.sh`. Он привязан к пути и значению, не распространяется на тот же токен в другом файле или на build. Добавление исключения требует доказательства, что это fake fixture, и ревью path+hash; общий skip для тестов запрещён.

Canary-тесты: `cd apps/api && .venv/bin/python -m pytest -q tests/test_secret_exposure_gate.py`. Они проверяют отказ на синтетический токен без его вывода даже из имени файла, tracked/untracked и rsync inventory, короткий пароль в URL БД, build/log и бинарную находку, отказ на пользовательский upload, отсутствие настроенного canary в публичных API-ответах `/health`, `/readiness`, `/categories`, `/service-templates`, отказе unauthenticated admin, неверном webhook и захваченных логах теста. Это адресная локальная проверка, не полное доказательство отсутствия секретов во всех авторизованных ответах, SMTP failure и production-логах.

Основной CI запускает source+deploy payload gate отдельным job; API, web и E2E зависят от него, а каждая web-сборка сканируется после `npm run build`. Плановый `e2e-smoke` тоже запускает source/payload и build gate. Перед release проверить свежие source/build результаты и нужные журналы через `--artifact`, приложить только сводку PASS/FAIL без секретов. Сканер намеренно высокоточный и может пропустить неизвестный формат токена, скрытый секрет в разрешённом бинарном медиа или непросмотренный runtime лог; отдельная staging/production проверка остаётся открытой.

## Узкое исключение тестовой сборки · 02.10.2026

После явного разрешения владельца source/payload inventory пропускает только `apps/web/.next-e2e-*` и `apps/web/.next-preview-*`: это незакоммиченные каталоги Next `distDir` из изолированных browser-прогонов. Проверка показала 14 таких каталогов, все с `cache`, ни одного tracked файла; 104 прежние находки `deploy-binary-unscanned`/`oversized-unscanned` относились только к ним. Обычный `.next` и приложения продолжают сканироваться по прежним правилам. Два точных SHA-256 синтетических Base32 TOTP-констант разрешены лишь в `apps/api/tests/test_identity_s06.py`; действительные секреты и совпадение в другом файле по-прежнему блокируют gate. Перед разрешением automatic approval review дважды отклонил правку как изменение security control. После разрешения объединённый `--source --build --deploy-payload` дал **PASS**; профильные canary/support тесты **14 PASS**, Ruff и diff-check PASS. Эти исключения должны оставаться ограниченными указанными путями при следующих изменениях генератора тестов.
