# Отмена, возврат и будущая выплата — локальный срез 02.10.2026

## Результат

Серверная отмена брони теперь сериализуется с созданием платежа по строке `Offer` и блокирует связанные `Payment` до проверки. Если существует ожидающий, успешный, внешний учтённый или возвращённый платёж, автоматический переход в `Cancelled` отклоняется с `409`. Слот и заявка сохраняются для ручного разбора. Платёж со статусом `failed` допускает обычную отмену. Проверен сценарий: отклонённая отмена ожидающего платежа → подписанный webhook успеха → бронь `Confirmed`, слот остаётся занятым.

Возврат выбирает адаптер по сохранённому `Payment.provider` и магазину, а не по текущему режиму checkout. Тестовый `stub` допустим только в local/test; внешний перевод не возвращается адаптером Букер; неподключённый или несовпадающий live-провайдер закрыт. Перед локальной записью `refunded` проверяются подтверждённый результат и точная сумма ответа адаптера. Второй TOTP-администратор остаётся обязательным. Повтор при `processing` и новый возврат после `partially_refunded` возвращают `409`, пока нет утверждённого серверного расчёта остатка и основания.

Guard будущей выплаты теперь проверяет статус брони, открытые заявки на возврат, возвращённый платёж и положительный нетто-остаток capture минус debit, помимо прежней сверки партнёра. Endpoint реальной выплаты отсутствует.

## Дополнение: долговечное намерение возврата

Перед вызовом адаптера API теперь отдельно фиксирует `RefundRequest.status=processing` и событие `payment.refund_dispatch_started` с исходным provider/merchant, суммой и ключом `refund-{request_id}`. После успешного ответа второй транзакцией сверяются статус, сумма, `full|partial`, provider refund ID и актуальные строки, затем вместе записываются статус, MoneyMovement и аудит. Сбой финализации после ответа провайдера оставляет заявку `processing`: повторное подтверждение отвечает `409` и не вызывает адаптер второй раз. Тест моделирует такой сбой после provider response; отдельный тест подменяет `kind` ответа при полной сумме и проверяет отсутствие ложного локального статуса.

Это защита от повторного вызова, а не автоматическое восстановление. Сбой после первого commit, ошибка адаптера или неоднозначный ответ оставляют `processing`; выплата заблокирована, оператору пока нужен ручной разбор первичных данных. Перед live rail необходимы provider query по неизменному ключу/ID, разрешение подтверждённого результата отдельным аудируемым действием и reconciliation со сверкой суммы/магазина; фиктивное успешное событие недопустимо. Полный API suite после двухэтапного refund и проверки `kind` **636 PASS, 9 SKIP**; он был запущен до последней точечной правки чтения ORM-атрибутов. После неё адресный refund/payout/reconciliation/cancel набор **56 PASS**; Ruff и diff-check PASS. Независимый read-only re-review проверки `kind` не нашёл новых конкретных P0/P1/P2. Перед сетевым вызовом суммы и ID копируются в локальные скаляры, чтобы истечение ORM-объектов после первого commit не открывало транзакцию во время ожидания адаптера; это соответствует документации SQLAlchemy 2.x. Общая оценка **84%** без staging/production и реального провайдера.

Приёмка recovery для будущего согласованного партнёра: запросить исход по исходному merchant и ключу без повторного refund; при подтверждённом успехе сверить payment/refund IDs, валюту, точную сумму и kind и дописать один debit, при подтверждённом отказе сохранить доказательство и разрешить новое действие через отдельный TOTP/CAS шаг, при неизвестном исходе оставить `processing` и блокировку выплаты. Проверить sandbox-сценарии «успех до сбоя БД», «сбой до вызова», «поздний ответ», «дубликат», «другой магазин/сумма» и «партнёр недоступен».
