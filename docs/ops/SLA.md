# SLA пилота Букер

Утверждённое рабочее окно: **ежедневно 10:00–22:00 МСК**. Выделенная дежурная смена и адресат просрочки пока не назначены.

| Ситуация | Цель ответа | Кто |
|----------|-------------|-----|
| Неявка / срыв даты в день события | 30 минут в рабочее окно 10:00–22:00 МСК | Оператор |
| Платёж прошёл, бронь не Confirmed | 2 часа в рабочее окно 10:00–22:00 МСК ежедневно | Оператор + доступ к `audit_logs` |

Для споров, обычных вопросов и иных категорий публичный срок первого ответа не вычисляется. Правила инцидентов ПДн и юридические сроки рассматриваются отдельно от этого support SLA.

Предложенный канал пилота — Telegram оператора; адресат и подключение не настроены, поэтому канал не публикуется. Эскалация возврата — two-eyes в админке (`POST /admin/refunds`).

## Состояние реализации 02.10.2026

Владелец утвердил общий график поддержки **ежедневно 10:00–22:00 МСК** 01.10.2026. Локальная конфигурация API использует это окно для двух кодов срочности (`event_day_no_show`, `paid_not_confirmed`) во все семь дней недели, включая праздники, пока `closed_dates=[]`. Начало окна включительно, 22:00 не входит; обращение до 10:00 начинает отсчёт в 10:00, остаток после 22:00 переносится на 10:00 следующего календарного дня. API сохраняет срок в UTC. Это расчётная цель первого ответа, не гарантия фактической смены. Локальная web-страница показывает график и срок в МСК только для обращений с серверным `response_due_at`.

Календарь можно переопределить через `BOOKER_SUPPORT_SLA_SCHEDULE_JSON`. Это JSON-словарь по кодам `event_day_no_show` и `paid_not_confirmed`; для каждого кода обязательны IANA `timezone`, список `weekdays` (0 — понедельник, 6 — воскресенье), `start`/`end` в формате `HH:MM` и список ISO-дат `closed_dates`. Если переменная явно пуста или календарь неполон, срок для этого кода не публикуется. Список закрытых дат нужно поддерживать в актуальном состоянии; пустой список означает, что особых выходных нет. Исключения для отдельных дат не утверждены и в конфигурацию не добавлены.

Production preflight дополнительно принимает только календарь, совпадающий с утверждённым графиком обеих срочных категорий, включая типы значений; пустой, повреждённый или отличающийся override останавливает запуск до смены кода/публичного текста по новому решению владельца. В локальном окружении ошибочный override скрывает срок и даёт диагностический сигнал мониторинга. После первого ответа, закрытия или reopen web показывает старую цель как историческую; новый срок автоматически не назначается.

При заданном графике время расходуется только внутри разрешённых окон, результат выдаётся в UTC с указанием смещения. Нестандартное время и окно на переходе DST не публикуют срок до отдельного календарного решения. Просроченное обращение без ответа оператора поднимается в защищённой admin queue с `response_overdue: true`; после первого ответа этот активный признак исчезает, а `first_response_late` сохраняет факт нарушения срока даже после reopen. Локальный ops monitor выдаёт агрегированный `support_overdue_unanswered` без PII и `support_sla_calendar_unavailable` при пустом/невалидном календаре. Внешний transport отключён; дежурный адресат, праздничные исключения, staging и production не проверены.
