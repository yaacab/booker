# Очередь email Букера

SMTP transport сохраняет письмо в той же транзакции, что и исходное действие.
Вызов `notify` не открывает SMTP-соединение. Если основная транзакция откатилась,
письмо не должно отправляться. Новая очередь использует hash содержимого/получателя
или явного semantic key; идентичные старые SMTP-ключи также распознаются.
Новая ссылка восстановления пароля создаёт отдельное письмо.

## Просмотр без отправки

Из установленного API-окружения:

```bash
python -m booker_api.notifications.worker
```

Выводит только количество записей по состояниям, без адресов, текстов и секретов.
Сначала примените штатный `alembic upgrade head`. Новые поля добавляет миграция
`b5c6d7e8f9a0_outbox_claims.py`; существующие письма сохраняются.

## Обработка сохранённой очереди

```bash
python -m booker_api.notifications.worker --deliver --limit 50
```

Команда не отправляет ничего, если `BOOKER_EMAIL_PROVIDER` не равен `smtp` либо
SMTP host отсутствует. Требуются существующие настройки `BOOKER_EMAIL_SMTP_HOST`,
`BOOKER_EMAIL_SMTP_PORT`, `BOOKER_EMAIL_SMTP_USER`, `BOOKER_EMAIL_API_KEY`,
`BOOKER_EMAIL_FROM`; STARTTLS обязателен. Секреты не помещаются в репозиторий.
При deployment оператор должен запускать ограниченный batch регулярно
(например, каждую минуту) через штатный job runner инфраструктуры. В рамках
разработки такой production job и реальные отправки не включались.
Существующий `POST /admin/email-outbox/retry` использует тот же обработчик и
существующую авторизацию platform admin/TOTP.

Обработчик открывает отдельную DB-сессию и выбирает только зафиксированные строки.
Атомарный UPDATE переводит письмо в `sending` с уникальным claim; claim фиксируется
до первого сетевого вызова. Другой обработчик не забирает эту запись. SMTP
Message-ID стабилен для записи; это помогает диагностике, но само по себе не
гарантирует дедупликацию на стороне почтового сервера.

## Состояния и повторы

- `pending`: сохранено и ожидает worker.
- `sending`: закреплено за worker, lease 10 минут.
- `sent`: SMTP сообщил об успешной отправке; это не подтверждение прочтения адресатом.
- `failed`: известная ошибка отправки; повторы через 60, 120, 240, 480 секунд,
  максимум пять попыток. Записи с исчерпанным лимитом требуют проверки оператора.
- `uncertain`: неизвестен исход после начала отправки либо истёк claim worker.
  Автоматического повтора нет: SMTP мог принять письмо перед потерей соединения.

У SMTP нет общего механизма exactly-once. Неоднозначные записи нужно сверять с
почтовым сервером по Message-ID и журналу. Интерфейс просмотра/ручного разрешения
таких записей остаётся частью незавершённого admin/operations блока master task;
не следует произвольно сбрасывать `uncertain` в `pending` без проверки риска дубля.
Тексты SMTP-исключений не пишутся в audit; фиксируются статус, номер попытки и ID.

Маркетинговые рассылки не создаются этим worker: он обрабатывает сохранённые
письма, созданные предметными сценариями. Для будущего marketing enqueue требуется
проверка явного consent. Доставка SMS/push и полный набор notification triggers
принимаются отдельно в продолжающемся разделе 21.
