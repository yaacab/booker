# Обработка сроков и уведомления

Команда работает с текущей БД API и не зависит от посещений сайта:

```bash
python -m booker_api.notifications.maintenance
```

По умолчанию это только просмотр количества просроченных подписок, кампаний
продвижения и резервов. Для применения ограниченной порции:

```bash
python -m booker_api.notifications.maintenance --run --limit 100
```

Лимит 1–100 применяется отдельно к каждому из трёх типов. Один вызов обрабатывает
не более 300 объектов и фиксирует изменения одной транзакцией. При deployment
нужно вызывать команду регулярно штатным job runner инфраструктуры; повтор
продолжает очередь и не повторяет уже обработанные переходы. Production job
в рамках разработки не создавался.

Текущие типы operational in-app уведомлений:

- `subscription.expired`: фактическое завершение платного периода, без изменения
  immutable условий старых сделок; повтор периода имеет собственный ключ.
- `promotion.expired`: кампания реально переведена в expired.
- `hold.expired`: истёкший резерв; новый действующий резерв той же сделки не
  отменяется и не освобождается. Повтор обработки не дублирует сообщение.
- `booking.cancelled`: фактическая отмена сделки её участником.
- `replacement.required`: заказчику предложено проверить состав и доступные
  варианты замены после отмены связанной с ролью сделки; замена не гарантируется.
- `payment.required`: обе стороны подписали договор, сделка перешла в ожидание
  оплаты. Уведомление не является подтверждением списания и предлагает проверить
  текущий резерв/условия перед оплатой.

Последние три типа создаются непосредственно в транзакциях исходных действий.
Сообщения адресованы текущим участникам нужной организации; персональная лента
не смешивает получателей. Ссылки подписок/продвижения выбирают конкретную
организацию в кабинете и не подменяют её другой при отсутствии доступа.

Команда использует только IN_APP. Она не запускает email/SMS/push и не создаёт
маркетинговые рассылки. SMTP worker описан отдельно в EMAIL_OUTBOX.md.
Отключение in-app provider отключает новые сообщения, но не отменяет применение
истёкших сроков. Новой миграции для этих hooks не требуется.

Раздел уведомлений ещё не принят полностью: остаются уведомления о препятствиях
подготовки события и полноценный срок действия предложения. В текущей модели
OfferVersion отдельного expiry нет; существующий виджет истекающих предложений
относится к hold. Не следует выдавать истечение hold за отдельную выдуманную
дату истечения предложения. Полная приёмка также включает consent и admin/ops.
