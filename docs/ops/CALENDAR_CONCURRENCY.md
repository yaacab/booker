# Конкурентные изменения календаря

Перед созданием open-слота и удержанием даты API берёт транзакционную
блокировку родительского ресурса (`Artist` или `VenueHall`). Это закрывает
проверку «свободно → запись» даже для пустого календаря: блокировка только
существующих слотов не защищала бы параллельную вставку.

Ресурсы пакета блокируются в стабильном порядке `(type, id)`, затем слоты
перечитываются под блокировкой. В PostgreSQL используется блокировка строки
через UPDATE без изменения значения; в SQLite — блокировка записи транзакции.
Тот же порядок входа используется импортом iCal и установкой/отменой отпуска.
Busy остаётся информационным наложением и не снимает существующий резерв.

Atomic hold до первого захвата сравнивает интервалы всех слотов пакета одного
ресурса с учётом календарных буферов. Пересечение означает 409 и полный откат;
два разных зала по-прежнему могут резервироваться одновременно. Защищены и
исторические пересекающиеся open-слоты, которые могли попасть в БД ранее.

## Проверка PostgreSQL

`BOOKER_TEST_POSTGRES_URL` должен указывать на отдельный тестовый сервер.
`tests/test_calendar_postgres.py` создаёт случайную схему `booker_test_*` для
каждого сценария и удаляет только её после теста. Нужны права CREATE SCHEMA.

```bash
BOOKER_DATABASE_URL=sqlite:// BOOKER_ENVIRONMENT=test \
BOOKER_TEST_POSTGRES_URL=postgresql+psycopg://test_user:test_password@127.0.0.1:5432/test_db \
pytest tests/test_calendar_postgres.py -q
```

Сценарии используют отдельные соединения и потоки. Первый поток останавливается
между проверкой и записью; второй должен дождаться его commit, затем получить
409. Проверяются пустой календарь и разные пересекающиеся слоты одного артиста
в разных событиях. Тесты не выдают последовательные запросы за concurrency.

В CI добавлен отдельный job `calendar-postgres` с PostgreSQL 16, миграцией
пустой базы до head и указанными тестами. В среде без переменной PostgreSQL
эти PostgreSQL-тесты явно пропускаются; SQLite не доказывает поведение PostgreSQL.

Новых миграций в изменении нет. Это прикладные блокировки, а не PostgreSQL
exclusion constraint: прямые SQL-записи и новые writers должны соблюдать
тот же протокол. Production job/deploy в рамках проверки не выполнялись.


## Версия предложения и резерв

Изменение OfferVersion, подтверждение условий и hold используют одну блокировку
Event. После ожидания перечитываются Offer/активная версия/Booking. Это не даёт
удержать старую согласованную цену одновременно с созданием новой версии.
Закрытое Event не принимает новые версии или подтверждения.

В том же PostgreSQL-файле добавлены три interleaving-проверки: hold → версия,
версия → hold, версия → подтверждение старого quote_id. Первый запрос доводится
до границы записи под блокировкой, второй ждёт, затем получает 409 по свежему
состоянию. Отмена альтернативной заявки и подписание договора дополняют эти сценарии;
на этом этапе были семь PostgreSQL concurrency cases.


## Отмена и владение резервом

Отмена блокирует Event, ресурс и слот в том же порядке, что hold, и перечитывает
Booking после ожидания. Слот освобождается только при собственном active hold
или состоянии Confirmed отменяемой сделки, если нет другого active hold или
другого бронирования, сохраняющего резерв. Отмена предложения в Negotiation
не освобождает удержание другой сделки на тот же слот. Закрываются все active
holds отменяемой сделки; чужие hold не изменяются.

В PostgreSQL проверена гонка разных событий на один слот: первое удержание
доходит до записи и приостанавливается, отмена альтернативы ждёт блокировку;
после commit первого запроса отменяется только альтернатива, резерв сохраняется.


## Подписание договора

Создание и новые подписи используют порядок Event → ресурс → слот.
После получения блокировки перечитываются договор и Booking; только новая
подпись проверяет активный собственный hold, версию и состояние сделки.
Повтор уже сохранённой подписи с правильным OTP возвращает результат без
побочных действий. Права участника проверяются и для такого повтора.

Седьмой PostgreSQL-сценарий останавливает подпись заказчика после проверки
резерва, запускает подпись исполнителя и доказывает ожидание Event lock.
После освобождения блокировки сохраняются обе подписи, два audit по сторонам,
одно уведомление payment.required и одно сообщение перехода к оплате.
Затем обе стороны повторяют запросы; количество этих записей не меняется.
Это не проверка гонок внешнего платёжного webhook или production-провайдера.

Дополнительно тот же disposable PostgreSQL fixture используется интеграционной
проверкой коммерческого отчёта: московский период, агрегации по источникам,
неизвестные комиссии и действующий резерв. Эта проверка отчёта дополняет concurrency-сценарии. Отчёт не подменяется SQLite
проверкой SQL агрегаций для production PostgreSQL.


## Capture, отмена и истечение резерва

Capture сериализуется через Event → resource → slot → Payment. expire_holds
получает те же первые три блокировки и перечитывает Booking/Hold после ожидания.
Четыре дополнительных interleaving-сценария проверяют capture/cancel и
capture/expiry в обоих порядках. Второй поток действительно ждёт первый.
Истечение не освобождает уже подтверждённый слот; capture после отмены или
истечения сохраняет факт денег, не воскрешает резерв и пишет конфликт оператору.
Дополнительные API-тесты проверяют закрытое событие, чужой hold и неверную сумму.

Текущий файл содержит 12 PostgreSQL cases: 11 конкурентных и один SQL-отчёт.
Локальный прогон на PostgreSQL 16.15: 12 passed (23.00s).
