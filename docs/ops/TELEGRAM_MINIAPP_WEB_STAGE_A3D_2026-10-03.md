## Реализовано

- `/telegram` загружает [официальный Telegram Web App script](https://core.telegram.org/bots/webapps)
  только на странице Mini App, берёт только сырой `Telegram.WebApp.initData` и
  передаёт его в серверные `/auth/telegram/prepare` и
  `/auth/telegram/complete`. Данные `initDataUnsafe` не используются как
  удостоверение личности. Неподтверждённый запрос не создаёт Booker-сессию.
- Первый вход показывает точный legal pack и отдельные обязательные действия;
  черновой локальный пакет называется черновым. Перед отправкой версия и хеши
  документов перечитываются. Повторный вход приводит к тому же `users.id`.
  Для operator/admin показывается запрос собственного Booker TOTP. Выбор
  рабочей роли ограничен customer/artist/venue.
- Обычный браузер без подписанного `initData` показывает границу Mini App.
  Предыдущий локальный Booker token очищается после успешной серверной
  подготовки Telegram proof. Для сценария нужен явный новый Booker token.
- CSP разрешает ровно `https://telegram.org` в `script-src`; тест периметра
  оставляет запрет остальных внешних origin. Страница исключена из индексации.

## Открытые границы

- Реальный Telegram WebView, bot configuration, staging и production не
  проверены. Нельзя объявлять живой вход работающим на основании мокнутого
  Web App script и синтетического HMAC.
- В staging/production новый аккаунт без email может войти, но новый доступ
  к организации требует `email_verified_at`; экран Mini App пока не собирает
  и не подтверждает email. Onboarding для такого аккаунта остаётся
  интеграционным gate. Локальный/test E2E работает при отключённой
  production email-политике.
- Внешний-only аккаунт пока не может привязать Telegram к существующему
  аккаунту без локального пароля; для этого нужен отдельный step-up. Яндекс/VK,
  реальная 2FA доставка и staging E2E остаются в общем плане.
