# Букер: локальная операционная диагностика, 02.10.2026

Статус: код и локальные тесты; установленные cron/systemd, staging, production и внешний канал оповещения не проверены. Это диагностический контур для оператора, а не круглосуточный alerting. Внешний транспорт по умолчанию отключён и запрещён production gate. Тестовый транспорт пишет JSONL только в локальный файл.

## Сигналы и пороги

| Источник | Условие по умолчанию | Ограничение |
|---|---|---|
| HTTP | 5 ответов 5xx по шаблону route или 10 запросов от 2000 мс за 5 минут | middleware пишет только шаблон route, метод, статус и время; checker читает максимум 20 000 строк, сообщает о насыщении выборки |
| Сервис | `booker-api.service` неактивен либо журнал недоступен | проверяется локально через `systemctl` и `journalctl`; это не внешний synthetic probe |
| Backup | последняя подтверждённая копия старше 30 часов, failed/invalid/legacy marker, checksum/size не совпали, найден более новый архив без binding | v2 marker и sidecar содержат ID, SHA-256 и размер опубликованного архива; checker пересчитывает SHA-256, поэтому I/O зависит от размера копии |
| Restore drill | последний подтверждённый drill старше 30 дней, failed/legacy, новая копия ещё не восстановлена, ID/hash/DB engine не совпали | v2 evidence связан с конкретной копией; SQLite проверяется в изолированном `/tmp`, PostgreSQL остаётся `UNKNOWN` |
| Email outbox | 50 pending/failed/sending, старейшее более 60 минут, failed с 3 попытками | `failed` сейчас может повторно отправляться: это повторный сбой, не терминальная DLQ |
| Reconciliation | открытое расхождение, последний run failed, последний успешный run старше 48 часов | age-порог включается только после `BOOKER_OPS_EXPECT_RECONCILIATION=true`; реальные отчёты партнёра не проверены |

Выход содержит только ключ сигнала, severity, агрегированное число и состояние `firing`/`reminder`/`recovered`. Получатели, письма, тела сообщений, платёжные ссылки, сырые URL и внешние reference не входят в метрики. Состояние и тестовый sink создаются с правами `0600`; checker ограничивает число ключей и повторяет событие не чаще раза в 60 минут. Настройки `BOOKER_OPS_*` перечислены в `apps/api/booker_api/config.py`.

## Операторская проверка

1. Проверить защищённый env, имя service, доступ к журналу и каталог `/var/backups/booker`.
2. Запустить `infra/run-booker-ops-monitor.sh` локально. Результат — только JSON с количеством активных сигналов/переходов; деталей PII нет.
3. Для локального упражнения использовать отдельные `--journal-file`, `--backup-dir`, `--state-file`, `--test-sink` и режим `BOOKER_OPS_ALERT_TRANSPORT=test_file` в непроизводственном окружении.
4. Пример `infra/cron-booker-ops-monitor.example` не установлен. Backup cron example направлен на `run-booker-ops-backup.sh`; после реальной установки требуется проверить, что marker появляется и меняется при успехе/отказе.
5. Для drill конкретной копии использовать `infra/run-booker-ops-restore-drill.sh <archive> <new-path-under-/tmp>` и соответствующий `*.evidence.json`. Скрипт делает приватную копию архива, повторно проверяет hash и только её передаёт SQLite verifier. Если нет v2 evidence, результат помечается `UNKNOWN` даже при успешном legacy drill.

Service unit содержит `--no-access-log`, чтобы обычный Uvicorn access log не записывал сырые URL поверх обезличенной телеметрии. До выпуска нужно проверить это на реальном журнале с безопасным canary query. Откат этого транша: вернуть прежний `ExecStart`, cron-команду и убрать `OpsHttpMiddleware`; новые marker/state-файлы можно оставить архивными. Возврат access log возобновит риск записи query string.

## Открытые границы

- При насыщении 20 000 строк checker сообщает о неполной выборке, но не восстанавливает пропущенные HTTP события. Для полноценного alerting нужен cursor/rollover учёт и внешний независимый probe.
- V2 manifest внутри архива и приватный sidecar содержат archive ID, UTC время, SHA-256 опубликованного архива, размер, DB engine, Alembic revision (если обнаружен), encryption/key ID без ключа и идентификатор набора вложений. Backup marker пишется после проверки архива и durable публикации; restore marker — после проверки hash, SQLite integrity/foreign keys/schema и файлов из manifest. Переход от legacy v1 требует нового backup и drill; v1 остаётся `UNKNOWN`.
- SHA-256 связывает marker и архив, но не доказывает происхождение, если злоумышленник может заменить оба. Sealed `.bke` дополнительно требует GCM tag и защищённый ключ. PostgreSQL restore verifier/RTO не реализован; synthetic PG contract и opt-in loopback harness не равны restore PASS.
- На диске нужен приватный каталог и достаточный объём/IO для временной проверенной копии архива. После `SIGKILL` временная копия в `/tmp/booker-ops-restore-*` может остаться и должна быть удалена оператором после проверки.
- Если запись v2 evidence оборвалась после публикации, новый архив сохраняется, checker сообщает `backup_unbound_archive`. Retention существующего backup-скрипта может удалить старый архив; его sidecar сам по себе не даёт PASS и требует отдельной housekeeping процедуры.
- SLA поддержки согласован: ежедневно 10:00–22:00 МСК. Локальный monitor считает только число открытых просроченных обращений без первого ответа (`support_overdue_unanswered`) и сигнализирует о недоступном календаре (`support_sla_calendar_unavailable`); тест проверяет отсутствие PII в snapshot. Внешний transport отключён. Маршрут дежурного и праздничные исключения не настроены; staging/production cron не проверены.
- Реальные исходящие уведомления и production cron/service не запускались этим траншем.

Откат v2: вернуть прежние backup/restore wrappers и manifest v1 только после проверки совместимости с нужным архивом; не удалять v2 архивы и sidecar. Monitor в старом режиме не должен считать v2 marker полным доказательством. Rollback производства этим локальным траншем не выполнялся.
