# Проверка вложений через clamd (локальный контур)

По умолчанию `BOOKER_AV_PROVIDER=manual`: загрузка остаётся в `quarantined`, а уполномоченный администратор может принять прежнее ручное решение с TOTP. Такое `clean` **не является AV-вердиктом**.

Для работы с установленным и обслуживаемым `clamd` задайте `BOOKER_AV_PROVIDER=clamd`, `BOOKER_AV_CLAMD_SOCKET` (по умолчанию `/run/clamav/clamd.ctl`) и при необходимости `BOOKER_AV_TIMEOUT_SECONDS` (по умолчанию 5). API использует только локальный Unix-сокет и `INSTREAM`; путь к файлу сканеру не передаётся. [Протокол clamd](https://docs.clamav.net/manual/Usage/ClamdProtocol.html) ограничивает входящий поток собственной настройкой `StreamMaxLength`; она должна быть не меньше `BOOKER_MAX_UPLOAD_BYTES`.

Порядок оператора после загрузки:

1. Файл остаётся в карантине и недоступен для скачивания и доказательств спора.
2. Администратор с TOTP вызывает `POST /admin/attachments/{id}/scan` с JSON `{"totp":"123456"}`. Это отдельное действие: загрузка сама по себе не запускает сканер.
3. Ответ `stream: OK` записывает `clean` и связанный с SHA-256 файла AV-вердикт; `FOUND` записывает `blocked`. Таймаут, недоступный сокет, ошибка лимита и неизвестный ответ возвращают 503 и оставляют карантин.
4. В режиме `clamd` ручное `clean` через `/scan-decision` получает 409. Старые ручные `clean` перестают быть доступными до повторного AV-сканирования. `blocked` нельзя разблокировать ручным `clean` в этом режиме.

На время сканирования запись переводится в карантин с идентификатором попытки. Параллельная проверка получает 409; результат применяется только к своей попытке. После ошибки токен освобождается, а после аварийного завершения процесса зависшую попытку можно повторить по истечении защитного интервала (не менее 30 секунд). `BOOKER_AV_TIMEOUT_SECONDS` ограничивает весь обмен с сокетом, а не только один `recv`.

Перед сканированием API сравнивает размер и SHA-256 сохранённого файла. После него те же метаданные проверяются при каждом скачивании; изменение файла переводит запись в `blocked`. Поле `downloadable` в Deal Room и допуск доказательства используют тот же предикат происхождения AV-вердикта.

Локально подтверждено только детерминированным fake-scanner через Unix-сокет и API-тестами. Для реального `clamd` остаются отдельные операционные проверки: установка и свежесть сигнатур, доступ процесса API к сокету, работа с тестовой сигнатурой, изоляция/мониторинг сканера, нагрузка и отказоустойчивость. Не включайте режим `clamd` в production без этих проверок: при недоступном сервисе файлы останутся в карантине.

Локальный проверочный прогон из `apps/api`: `.venv/bin/python -m pytest -q tests/test_attachment_av.py tests/test_attachments.py tests/test_alembic.py`. Он использует fake-сокет и временные БД, не запускает реальный ClamAV. Перед rollout дополнительно прогоните Alembic `upgrade head` на защищённой копии старой непустой БД, зафиксируйте время и проверьте, что старое ручное `clean` больше не скачивается после переключения `BOOKER_AV_PROVIDER=clamd`.
