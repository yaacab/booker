# Единый аккаунт: необязательные email и локальный пароль

**Статус:** локальный кандидат этапа A2. Действующая БД, staging и production
не менялись. Полный запуск по фиксированному реестру остаётся **59,00%**.

## Состав

- Alembic `a10f12e34f56` после `a09f01e23f45` разрешает `NULL` в
  `users.email` и `users.password_hash`. Старые значения, ID и сессии не
  заменяются. Новые аккаунты не получают выдуманный email или пароль.
- Ограничение БД не позволяет ставить `email_verified_at`, если адрес отсутствует.
  Администратор и оператор всё ещё требуют подтверждённый email и TOTP;
  соответствующие SQLite-триггеры сохраняются при перестройке `users`.
- Проверка миграции сравнивает нарушения FK до и после. Уже существующие
  нарушения не приписываются этой миграции; реальный release gate отдельно
  требует чистый источник и подтверждённый restore.
- API отдаёт `email: null` без утверждения проверки адреса; вход с локальным
  паролем для аккаунта без `password_hash` отвергается. Профиль показывает
  «Email не добавлен», кабинеты корректно принимают необязательный адрес.
  Почтовые очереди не создают письмо без адресата.

## Проверка и границы

Копия заполненной SQLite с действующим пользователем и сессией обновлена до
новой ревизии без изменения исходного файла. Проверены неизменность старых
значений, всех пользовательских триггеров, `integrity_check`, `foreign_key_check`,
вставка аккаунта без credentials и отказ фиктивной email-верификации/админ-роли.
Тесты с историческими тестовыми нарушениями FK проверяют отсутствие **новых**
нарушений. PostgreSQL-репетиция остаётся opt-in и не считается выполненной без
`TEST_POSTGRES_DSN`. Draft schema manifest остаётся `manual_block`.

Локальные проверки кандидата: полный API **787 PASS/9 SKIP**; адресные
schema/Alembic **35 PASS/1 SKIP**; web TypeScript, **21 unit PASS** и Next build
PASS. Ruff, `git diff --check` и source/deploy-payload secret gate PASS.
Настоящий браузерный сценарий с внешним провайдером и PostgreSQL здесь не
проверен.

Этот этап **не** включает внешнюю авторизацию: ещё нужны проверка Telegram
`initData`, legal-pack/pending-auth gate, Яндекс/VK callback, привязка без
автоматического слияния по email, собственная 2FA, E2E старых сессий и staging.
Для фактической БД сначала установить engine и source revision, сделать
sealed backup с uploads и restore, затем утвердить миграцию и проверить её
на копии и staging. Откат данных после создания аккаунтов с `NULL` требует
отдельного плана: автоматический downgrade намеренно закрыт.
