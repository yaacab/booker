# Шифрование TOTP при хранении — локальный кандидат

Срез: 02.10.2026. Отдельный worktree от проверенного SHA `ce0668176793f4546b640466f82fb4056967e26b`. Этот этап не закрывает S06 и не разрешает staging/production cutover.

## Что изменено

- `User.totp_secret` остаётся обычным Base32 для существующих вызовов auth, но SQLAlchemy шифрует значение перед записью и расшифровывает после чтения. В БД лежит только `fernet:v1:` плюс аутентифицированный шифротекст. Открытое старое значение или повреждённый токен при чтении блокируются.
- `a04f56b78c90` сначала проверяет **все** старые записи и ключ, затем преобразует допустимые Base32-значения. Уже зашифрованную запись при повторе проверяет и сохраняет. Неизвестное значение требует ручного разбора; на PostgreSQL колонка расширяется до `TEXT`, на SQLite длина `VARCHAR` не ограничивает хранение и таблица не перестраивается, чтобы сохранить триггеры прав.
- SQLite migration/runtime trigger запрещает новую запись открытого TOTP через прямой SQL; PostgreSQL получает проверку префикса. Тестовый прямой SQL fixture E2E теперь записывает шифротекст.
- Staging и production требуют отдельный ключ `BOOKER_TOTP_ENCRYPTION_KEYS` из защищённого хранилища. В local/test без явного ключа работает только фиксированный тестовый ключ. Список Fernet-ключей читается слева направо: новые записи — первым ключом, старые — любым из списка.

## Операционные границы

До запуска новой версии на действующей БД нужны подтверждённый engine/source revision, sealed backup с вложениями и проверенный restore, один и тот же ключ в миграции и API, ручное ревью schema manifest (`manual_block`) и staging E2E входа/восстановления. Старый API не сможет проверить TOTP после преобразования БД; откат приложения требует совместимого снимка данных и конфигурации. Data rollback не атомарен.

Не удалять старый ключ из списка, пока все записи, зашифрованные им, не перенесены и не проверены; автоматического массового перевыпуска этим изменением нет. Потеря всех ключей блокирует служебный вход. Ключи, открытые TOTP и recovery codes не писать в git, чат, логи и результаты тестов. Шифрование действующей БД не удаляет исторические копии; доступ к старым архивам остаётся под политикой backup/retention.
