# Техническое подтверждение неизменяемого черновика — 02.10.2026

## Статус

P0-B реализован и проверен локально в общем dirty дереве. Это технический контур доказательств, а не опубликованный прямой договор и не утверждённая простая электронная подпись. Commit, push, deploy, SSH, PostgreSQL, staging, production и правки `docs/legal/**` не выполнялись.

## Что связано в один снимок

- Сервер формирует канонический текст из принятой активной `OfferVersion`: все суммы, валюта, комиссия, аванс, остаток, обеспечение, нормализованный график платежей и полный текст условий.
- В снимок входят стороны и их организации, booking/request/resource/requirement, событие, город, дата, слот и его начало/окончание. Текст получает SHA-256, `offer_version_id`, версию шаблона, редакцию юридического пакета и эффект `technical_draft_acknowledgement`.
- `Contract` и каждое подтверждение хранят один и тот же hash/version/effect. Deal Room показывает точный текст, hash, историю offer ack и технических подтверждений. Старые записи остаются `legacy_unbound` и не получают выдуманного доказательства задним числом.
- Создание новой версии оффера, подтверждение и выпуск черновика сериализуются по строке оффера. Выпуск снимка и изменение состава события дополнительно используют общую блокировку строки события; после выпуска изменение требований закрыто с `409` до отдельного сценария изменения сделки. Подтверждение и начало платежа проверяют активную принятую версию, booking state, сохранённый текст/hash и две совпадающие неизменяемые записи подтверждений.

## Код и полномочия

- Код шестизначный, 15 минут, отдельный для каждого уполномоченного пользователя и стороны; в БД хранится salted PBKDF2 hash. Viewer код не получает.
- На каждом действии повторно проверяется текущая роль `owner/admin/manager` и выбранная организация. Один пользователь не может подтвердить обе стороны. Использованный или просроченный код не принимается.
- После истечения пользователь может запросить новый append-only challenge. Пока прежний код действует, повторная выдача закрыта с 409. Полномочия и неизменность снимка проверяются и при перевыпуске; уникальный challenge ID входит в ключ доставки.
- Локальный `dev` in-app transport держит приватное содержимое только в ограниченной памяти процесса до TTL; audit содержит только метаданные. Одноразовый SMTP-код отправляется синхронно и не записывается в `EmailOutbox`. Production требует SMTP host. API сообщает доставку отдельно для customer/supplier и считает общий результат успешным только для обеих сторон.

## Миграция и выпуск

Ревизия `ffbc123cd4e6` идёт после `feab012bc3d5`. Она добавляет связь контракта и подтверждений с offer version/hash/effect, очищает legacy plaintext OTP, создаёт append-only challenges и SQLite/PostgreSQL guards. SQLite migration принимает переходное состояние, где runtime `create_all/ensure_missing_columns` уже создал новые поля или таблицу.

## Открытые gate

- Юрист должен утвердить оператора, прямой договор, соглашение о простой электронной подписи, идентификацию и полномочия. До этого интерфейс последовательно говорит о техническом подтверждении черновика.
- Нужны фактический запуск PostgreSQL concurrency/migration rehearsal, staging с реальной доставкой кода, production config и мобильный сценарий на устройстве.
- P2: синхронный ephemeral SMTP отправляет код до commit транзакции. При редком отказе commit получатель может увидеть недействительный код; корректное закрытие требует purpose-built защищённой очереди или отдельного протокола состояния доставки.
- Legacy `legacy_unbound` записи требуют отдельного разбора первичных данных; безопасный backfill точного принятого текста невозможен без доказательств.
