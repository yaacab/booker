- Новый запрос сброса пароля сохраняет хеш токена до попытки доставки, отправляет каждую новую ссылку временным SMTP-объектом и не пишет тело ссылки в `EmailOutbox`. Повторная выдача создаёт другой токен; старые ссылки очищаются при старте identity router и не уходят повторно.
- В production первый администратор без TOTP не получает bearer для административных маршрутов. До входа он может запросить одноразовое подтверждение по SMTP по паролю и email, затем подтвердить 32-символьный Base32 секрет кодом приложения. Подтверждение отзывает прежние сеансы. Если TOTP уже включён, тот же email proof не заменяет его: ротация требует текущий TOTP, пароль и новый код. Сброс пароля администратора также требует действующий TOTP.

## Открытые требования S06

1. **Потеря authenticator:** email и пароль сами по себе не должны заменять уже включённый TOTP. Нужен утверждённый порядок независимой проверки личности и полномочий, минимум два разных оператора либо иной независимый фактор, аудит, отзыв всех сессий, уведомление владельца, проверка повторного входа. Пока такого протокола и исполнителя нет, восстановление потерянного TOTP закрыто fail-closed. Не добавлять mailbox-only self-service.
2. **Владение email:** локальный verify-flow теперь существует: новые регистрации при включённом gate получают отдельный одноразовый email proof; создание организации, добавление участника и принятие приглашения до подтверждения блокируются. Исторические аккаунты не получают фиктивный `email_verified_at`; для новых грантов требуется подтверждение. Новое назначение администратора без него блокируют API и DB trigger, прежних администраторов миграция не лишает доступа. Смена адреса через API сейчас не поддерживается; до её появления нужна отдельная процедура с проверкой нового ящика и отзывом привязанных полномочий. Реальная почта, миграция фактической БД и staged rollout не проверены.
3. **Реальная доставка:** SMTP и историческая БД, запуск startup scrub на фактическом engine, переходы при ошибке/повторе провайдера, mobile/keyboard путь и staging/production не проверены. Секретное письмо не хранится для ретрая, поэтому пользователь должен запросить новый код после сбоя.
4. **Релизный кандидат:** полный локальный API прогон прошёл на dirty дереве, а не на закреплённом SHA/CI артефакте. Это не закрывает P08/O04.

S06 получит свои 2 балла только после приёмки всех его условий. Код с локальным green не разрешает включать production регистрацию или считать вход/восстановление администраторов проверенными на VPS.

## Решение для потерянного TOTP, требующее утверждения владельца

Обычная ротация по-прежнему требует текущий TOTP. При утрате устройства ни владение почтой, ни сброс пароля не дают права отключить второй фактор. Временный безопасный исход — заблокированный административный доступ при сохранённых данных и полномочиях.

Для отдельного восстановительного процесса нужно заранее назвать двух независимых утверждающих лиц (включая порядок для единственного администратора), допустимое доказательство личности и полномочий вне email, канал уведомления владельца, срок ожидания, правило экстренного случая и срок хранения доказательств. После их решения технический процесс должен выдать однократное короткоживущее разрешение на привязку нового устройства, потребовать свежий пароль и код нового TOTP, отозвать все прежние сессии и оставить неизменяемый аудит. До фиксации этих решений endpoint восстановления не открывать.

Для общего подтверждения email новые адреса должны начинать в состоянии `pending`; исторические записи нельзя автоматически объявлять подтверждёнными. Подтверждение нового адреса не заменяет принятие юридических документов, пароль или TOTP. При внедрении отдельно проверить прямое добавление участника в организацию, принятие приглашения и назначение администратора: одна лишь совпавшая строка email не доказывает владение почтовым ящиком.
