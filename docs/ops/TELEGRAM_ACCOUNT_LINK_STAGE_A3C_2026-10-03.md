## Реализовано

- `GET /me/identities` показывает только способы входа и даты, без Telegram ID
  или токенов. Операторский серверный allowlist разрешает только эти
  конкретные маршруты управления собственным аккаунтом.
- `POST /me/identities/telegram/link` принимает одноразовый pending proof из
  проверенного `initData` **и** действующую Booker-сессию. Перед записью
  повторно проверяются текущий пароль и, для operator/admin, Booker TOTP.
  Сессия и полномочия перечитываются под блокировкой после получения proof.
  Чужой Telegram subject и второй subject для того же аккаунта отклоняются;
  совпадение имени/email ничего не связывает. Новый `User` не создаётся.
- `POST /me/identities/telegram/unlink` требует тот же step-up. Сейчас
  оставшимся рабочим способом может быть только подтверждённый повторным
  вводом email+пароль: Яндекс/VK ещё не реализованы. После отвязки другие
  Booker-сессии отзываются, текущая остаётся; бывший Telegram subject не
  получает прежний аккаунт повторно.
- Оба изменения создают audit-событие с хешем subject и статическое
  уведомление в кабинете; при настроенном SMTP — уведомление без сырых
  доказательств входа. Пароль, TOTP и pending token в audit/notice не пишутся.
