## Установленные факты из текущего кода

1. `apps/api/booker_api/routers/catalog.py`, `GET /catalog/search`: `Artist.city` и `Venue.city` фильтруются в SQL, но обе выборки завершаются `.all()` до проверки публикации, календаря и большинства фильтров. Параметров `limit`/`cursor` у поиска нет; ответ содержит все прошедшие профили в двух массивах `items` и `venues`. Порядок результата явно не закреплён. Исключения, формат, travel, часть бюджетных/гостевых условий и маскирование busy слотов применяются после загрузки строк.
2. Для каждого артиста `artist_publication_eligibility` отдельно читает наличие слота, тарифа и представителя; затем поиск читает все его слоты и тарифы. Для каждой площадки `venue_publication_eligibility` отдельно читает ID залов, слоты залов, тариф, фото и представителя; поиск дополнительно читает залы, слоты каждого зала, тарифы и все разрешённые фото, хотя для карточки берёт только `photos[0]`. Это N+1; при многих залах число запросов растёт ещё быстрее. `open_slots_unmasked` сравнивает открытые и busy интервалы в Python, поэтому рост числа слотов увеличивает не только объём чтения, но и работу по маскированию.
3. `apps/api/booker_api/publication_eligibility.py` является действующим серверным gate: публикация, проверка профиля, положительный тариф, подтверждённые права на медиа, представитель, подтверждённый горизонт календаря не менее 30 дней и записи календаря; для площадки также claim, moderation и все залы. Оптимизация обязана сохранять именно этот результат, включая отсутствие research/неаттестованных фото в публичной выдаче. `GET /catalog/public-index` имеет `cursor`/`limit` в ответе, но сначала материализует и проверяет все профили; это отдельный путь для sitemap, не пагинация поиска.
4. `apps/web/app/search/page.tsx` делает `cache: "no-store"` запрос полного `/catalog/search`, после чего сразу рендерит все карточки. `apps/web/components/CatalogResultCard.tsx` показывает прямой URL обложки площадки через `<img loading="lazy" decoding="async">`; CSS задаёт 76×76 px и 48×48 px на узком экране. В `apps/web/components/VenueProfileClient.tsx` галерея отображает все URL; первое фото `eager`, остальные `lazy`. Для этих `<img>` нет `srcset`/`sizes` и варианта файла под размер экрана. Из CSS-размера нельзя вывести сетевой вес: исходный файл может быть гораздо больше. Текущий `next.config.ts` не задаёт image-loader/remote patterns. Права фото и аттестация URL проверяются на API, но фактические размер, формат, cache headers, скорость стороннего хоста и поведение на телефоне здесь не измерены.
5. `apps/api/booker_api/models.py`: `Artist.city` и `Venue.city` не имеют индекса; у `AvailabilitySlot` есть одиночные индексы `resource_id` и `starts_at`, у `VenuePhoto` — `venue_id` и уникальная пара `(venue_id, photo_url)`. Вывод об эффективности дополнительных индексов для PostgreSQL требует отдельного EXPLAIN на кандидате схемы и реальных распределениях.

## Изолированный локальный эксперимент

Запущен 02.10.2026 через `apps/api/.venv/bin/python` с `PYTHONDONTWRITEBYTECODE=1` и `PYTHONPATH=/home/art67/booker/apps/api`. Временный скрипт `/tmp/booker_p07_benchmark_20261002.py` создаёт только `sqlite:///:memory:` и десять нужных таблиц SQLAlchemy; общие БД, папки тестовых output и файлы репозитория не использует. SQLite `3.53.1`, SQLAlchemy `2.1.1`. Набор: 100 аттестованных артистов и 50 аттестованных площадок Москвы, одна организация/представитель и один тариф на профиль, один зал и одно разрешённое фото на площадку, четыре открытых слота на ресурс; всего 600 слотов. Это верхняя граница KPI пилота 80–150 founding-профилей по **количеству**, но распределение и содержимое полностью искусственные.

Вызван непосредственно `search_catalog(city="Москва", ...)` без фильтров. Счётчик SQLAlchemy `before_cursor_execute` установлен только после заполнения базы; учтены SQL-команды самого поиска. Один прогревочный вызов и три повторных вызова, каждый с новым `Session` на том же in-memory engine:

| Прогон | Результат | SQL statements | Время Python-вызова | JSON UTF-8, без HTTP/gzip |
|---|---:|---:|---:|---:|
| Прогрев | 100 артистов + 50 площадок | 952 | 217,91 мс | 62 923 байта |
| Повтор 1 | то же | 952 | 186,07 мс | 62 923 байта |
| Повтор 2 | то же | 952 | 189,17 мс | 62 923 байта |
| Повтор 3 | то же | 952 | 188,89 мс | 62 923 байта |

**Медиана повторов: 188,89 мс.** Для этого набора число запросов объясняется кодом: 2 выборки профилей + 100 × 5 запросов на артиста + 50 × 9 запросов на площадку = 952. При нескольких залах на площадку число изменится. Размер JSON измерен отдельной сериализацией результата после таймера; время JSON/HTTP, SSR, сети и браузера в 188,89 мс не входит.

`EXPLAIN QUERY PLAN` на той же заполненной базе (точные строки SQLite):

```text
artist_city   [(2, 0, 216, 'SCAN artists')]
venue_city    [(2, 0, 216, 'SCAN venues')]
slot_resource [(3, 0, 61, 'SEARCH availability_slots USING INDEX ix_availability_slots_resource_id (resource_id=?)')]
venue_photo   [(4, 0, 61, 'SEARCH venue_photos USING INDEX ix_venue_photos_venue_id (venue_id=?)'), (35, 0, 0, 'USE TEMP B-TREE FOR ORDER BY')]
```

Формы проверенных запросов: `SELECT id FROM artists WHERE city='Москва'`; аналогично `venues`; `SELECT id FROM availability_slots WHERE resource_type='artist' AND resource_id='artist-000'`; `SELECT id FROM venue_photos WHERE venue_id='venue-100' AND photo_rights_status IN ('owned','licensed','official_permission') AND rights_attested_at IS NOT NULL AND rights_attested_by_user_id IS NOT NULL ORDER BY sort_order,id`. Это планы **выбранных репрезентативных SQL-форм**, не EXPLAIN каждого ORM-запроса и не план PostgreSQL. In-memory SQLite, один процесс, тёплый CPU/cache, один зал, один URL фото, отсутствие busy/held слотов и реальной конкуренции делают задержку непригодной как прогноз p95 staging или мобильного UX.

## Предлагаемое решение (не реализовано)

1. Ввести версионированный пагинированный поиск, сохранив существующие названия полей карточек и серверный gate публикации. Вариант совместимого перехода: новый `/catalog/search-page` с `limit` (по умолчанию 24, максимум 50), opaque `next_cursor`, `has_more`, а также прежними массивами `items`/`venues`; старый `/catalog/search` временно оставить для клиентов и ограничить/вывести из эксплуатации после перевода web и проверки потребителей. Курсор должен содержать версию, нормализованный fingerprint фильтров и последний просмотренный ключ `(kind, id)`; несовместимый курсор возвращает 400. Установить порядок `kind, id` явно. Смена параметров поиска начинает страницу заново. Не ограничивать профили до проверки eligibility: иначе страницы могут стать пустыми и пропустить доступные карточки. При пакетном сканировании курсор указывает на последнего **просмотренного** кандидата; проверять до заполнения страницы или исчерпания кандидатов, с ограниченным размером одного DB batch и корректным `has_more`. Исследовательский `/catalog/demo/venues` и sitemap `/catalog/public-index` сохраняют свои отдельные контракты и права доступа.
2. Свести проверки eligibility и связанные данные в групповые запросы по ID текущей пачки. Отбор кандидатов максимально перенести в SQL: город, категория, статус публикации/верификации, календарный горизонт, положительный тариф, наличие представителя и аттестованного медиа; для площадок — claim/moderation/зал. Финальная проверка тем же серверным gate или доказанно эквивалентной пакетной функцией обязательна, особенно для всех залов, `required_through`, прав фото и маскировки busy. Слоты грузить только для кандидатов страницы и нужного окна; не превращать `busy` в свободный слот. Для обложки получить одну первую разрешённую фотографию на площадку, не всю галерею. Устранить зависимость SQL count от числа карточек в странице; проверить многозальные площадки и скрытые/неаттестованные профили отрицательными сценариями.
3. Предложить миграции индексов после сравнения планов: `artists(city, category, id)`, `venues(city, id)`, `availability_slots(resource_type, resource_id, starts_at)` и, если eligibility по горизонту выигрывает, отдельный вариант с `ends_at`; `venue_photos(venue_id, sort_order, id)` или частичный индекс разрешённых/аттестованных фото. Одиночный `resource_id` уже существует — новый индекс допустим только при доказанном выигрыше чтения и приемлемой цене записи. Проверить `EXPLAIN QUERY PLAN` на SQLite и `EXPLAIN (ANALYZE, BUFFERS)` на PostgreSQL после `ANALYZE`, на датах с плотными слотами и несколькими залами. Не создавать индексы «на глаз» в общей базе.
4. Обновить web для page/cursor и последовательной дозагрузки с сохранением всех фильтров, глубокой ссылки и состояния back/forward. Сразу после первой страницы рендерить только её карточки; доступная кнопка «Показать ещё» либо эквивалентный наблюдаемый механизм. Показывать окончание списка и ошибки следующей страницы без потери уже загруженных карточек. Измерять SSR и hydration отдельно от API.
5. Для разрешённых фото подготовить управляемые версии thumbnail и gallery/hero (например, AVIF/WebP с JPEG fallback), `srcset`/`sizes`, точные intrinsic dimensions и устойчивые cache headers. Сторонний URL не превращать автоматически в публичный asset без действительного разрешения; отсутствующие/недоступные медиа заменять нейтральным placeholder без стороннего запроса. Не ослаблять `PUBLIC_MEDIA_RIGHTS` и аттестацию ради скорости. Проверить фактические форматы, байты и происхождение URL перед выбором способа доставки.

## Измерения для закрытия P07

Это **предлагаемые пороги приёмки**, а не полученные результаты или изменение веса P07.

- Данные: 80–150 профилей, близкие к реальному пилоту по типам/категориям, доле скрытых и опубликованных, 1–несколько залов, разным тарифам, 30-дневному горизонту, открытым и busy слотам. Зафиксировать генератор/снимок без персональных данных, SHA миграции и точные количества. Проверить поиск без фильтров, категорию, дату, бюджет, гостей, исключения и сортировку, а также повторную публикацию/снятие с публикации между страницами. Исследовательские карточки не попадают в публичный поиск.
- API/БД: для первого и следующего page получить query count, `EXPLAIN`, p50/p95 из не менее 20 запросов каждого сценария на одинаковом окружении, объём несжатого и сжатого ответа. Целевой ориентир: ≤25 SQL statements на страницу 24 карточки и p95 API ≤300 мс на представительном staging; если профиль/многозальность требуют другого бюджета, закрепить его **до** финального прогона вместе с причиной. Количество запросов не должно линейно расти с числом возвращённых карточек. Провести отдельный PostgreSQL-план и проверить влияние индексов на запись; зафиксировать откат миграции.
- Корректность ответа: страницы без дублей/пропусков на неизменном наборе, `limit` и cursor валидируются, фильтры и порядок стабильны, старый потребитель получает ожидаемую форму до миграции. Сравнить результат с текущим gate на матрице опубликованных/скрытых профилей и фото; пустой batch не должен ошибочно означать конец выдачи. Цена остаётся только серверной; никакой прогноз фото/доступности клиент не выдаёт за подтверждённый факт.
- Мобильный путь: на реальном Android среднего класса и iPhone (либо явно указать использованный device lab), Wi‑Fi и ограниченный 4G, холодный и тёплый cache, записать 5–10 прогонов первой страницы и профиля. Сохранить HAR/Performance trace: фактические URL, `Content-Type`, intrinsic и rendered dimensions, transferred/decoded bytes каждой картинки, cache hit/miss, количество запросов, LCP и p75/p95 времени появления первой полезной карточки. Ориентиры для согласования: первая видимая группа изображений ≤500 KiB переданных байт, thumbnail ≤100 KiB каждый, основное фото профиля ≤250 KiB, LCP ≤2,5 с на согласованном профиле сети; если внешние лицензированные фото не позволяют достичь лимита, оформить решение по правам/доставке отдельно. Не подменять реальные байты CSS-размером или Lighthouse score.
- Evidence для реестра: точный SHA/dirty diff, окружение, SQL планы и счётчик, latency/пейлоад, HAR и журнал правомерной публикации выбранных фото, регрессионные проверки и воспроизводимые результаты. Только после выполненных измерений и исправлений можно решать, закрыт ли P07; этот sidecar закрытия не доказывает. До тех пор P07 = ○, общий счёт остаётся 55/100, остаток до полного запуска 45 баллов.
