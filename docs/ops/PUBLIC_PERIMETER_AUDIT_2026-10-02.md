# Букер — публичный периметр, локальный hardening, 02.10.2026 МСК

Статус: безопасные гостевые GET/HEAD и TLS handshake проверены на действующих `bukergo.ru`, `bookergo.ru`, `bukergo.online`; изменения ниже находятся только в локальном рабочем дереве. Production nginx/API/web не обновлялись. SSH, учётные записи и реальные платежи не использовались.

`X-Nextjs-Prerender` на главной пришёл дважды; причина в установленном стеке не проверена. `s-maxage=31536000` позволяет промежуточному shared cache держать HTML до года, поэтому локальный nginx конфиг теперь заменяет upstream cache policy для web страниц. В установленном production этого исправления ещё нет.

## Локальные исправления

- `infra/nginx/bukergo.ru.conf`: `server_tokens off` во всех server blocks; HTTPS HSTS `max-age=604800` без `includeSubDomains`/`preload`; общий CSP и защитные заголовки с `always` на каноне, HTTPS/HTTP редиректах, API, ошибках и locations с собственным `add_header`. `/_next/static/` сохраняет годовой immutable cache для hashed ассетов. Общий web route скрывает upstream Cache-Control и ставит `private, no-cache, no-store`; API сохраняет свои cache headers. `/api/internal/readiness` публично отдаёт 404.
- CSP: `default-src 'self'`, закрыты `object-src` и чужой `base-uri`, `frame-ancestors 'self'`; код/стили с текущим inline bootstrap допускают `'unsafe-inline'`. Изображения и медиа допускают HTTPS, в том числе QR от `api.qrserver.com`; `connect-src 'self'`. Это промежуточная совместимая политика: `'unsafe-inline'` снижает защиту от XSS. Более строгие nonce/hash требуют отдельной проверки всех страниц и внешних интеграций.
- `apps/web/next.config.ts`: `poweredByHeader: false`. Web переключатель рабочего пространства читает флаг из авторизованного `/me`, сохраняя совместимость со старым API при последовательном переключении версий.
- API `/health` отвечает только `{ "ok": true }` с `Cache-Control: no-store`. Production `/readiness` требует platform-admin bearer **и TOTP-verified session/header**; локальные тесты могут читать его без входа. Отдельный `/internal/readiness` возвращает только DB status и предназначен для прямого loopback порта 8030; приложение в production отвергает не-loopback и запрос с `X-Forwarded-Proto`, а nginx блокирует публичный URL. `infra/deploy-vps.sh` использует `curl -fS` к нему, чтобы 503 не проходил как успех. Этот probe не является полным release gate для платежей или owner inputs.

## Локальная проверка и границы

Адресные API tests покрывают минимальный health, admin/guest/TOTP readiness, DB-fail probe, доверенный и чужой Origin; статические config tests проверяют header inheritance, CSP/HSTS, cache classes и закрытый публичный путь. Полный API suite до последнего TOTP guard **561 PASS, 6 SKIP**, после него профильный health/proxy/TOTP suite **17 PASS**; web unit **11 PASS**, TypeScript и свежий Next production build PASS. Браузерный smoke на `/`, `/login`, `/search` под введённой CSP прошёл: Chromium видел inline scripts и не выдал CSP violations в этой выборке. Локальный Next runtime на loopback вернул 200 без `X-Powered-By`; без nginx он по-прежнему отдаёт исходный годовой `s-maxage`, а новая proxy policy не была выполнена. Source/payload/build secret gate, Ruff, shell syntax и `git diff --check` PASS. Независимое read-only review подтвердило исправление TOTP-обхода, не нашло иных новых P0/P1 и оставило deploy rollback P1. Реальный QR и авторизованные сценарии под CSP не проверены. На машине нет nginx binary, поэтому `nginx -t` и поведение фактической reverse proxy ещё не подтверждены; перед любым deploy нужен `nginx -t` с теми же include-файлами, затем staging browser/API/error/redirect smoke и проверка настоящих заголовков. Production по-прежнему отдаёт старые headers до отдельного выпуска.

**Дополнение по release-блокеру:** после этого аудита `infra/deploy-vps.sh` заменён локальной [release transaction](RELEASE_TRANSACTION_2026-10-02.md). Отдельный каталог хранит API venv, web `node_modules` и `.next`; переключается только `current`, а при post-switch отказе возвращаются предыдущий symlink, конфиги и сервисы. Fake-root тесты подтверждают выбранные failure paths. Действующий production всё ещё работает по старому механизму; staging и реальный nginx/VPS не проверены. Релиз на production не разрешён одним лишь локальным тестом. При ручном восстановлении проверить согласованность API/web/nginx и отдельно состояние данных; `/health` сам по себе не доказывает работоспособность DB.
