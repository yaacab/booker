# Букер — запросы субъекта данных, локальный P0-F срез 02.10.2026

Статус: техническое ядро в dirty рабочем дереве. Политика сроков хранения, основания обработки, права на медиа и порядок юридического решения не утверждены здесь. Автоматическое удаление, генератор полного архива и production действия выключены. `docs/legal/` не менялся.

В коде нет ранее подтверждённого общего erasure/export/restriction маршрута. Новые таблицы `data_subject_requests`, `data_subject_request_events`, `legal_holds` сохраняют запрос, переходы и внутреннее удержание отдельно от пользовательских данных. Миграция `fd9a012bc3d4` следует за `fc8f901ab2c3`; schema manifest остаётся черновым и `manual_block`.

## Реализованный контракт

- Пользователь создаёт `access|export|restrict|delete|correct`, видит только свои запросы/события и может отменить `pending|needs_info` с точным `If-Match`. Создание требует `Idempotency-Key`; повтор с другим типом отклоняется. `correct` принимает только имя поля (`email|phone|full_name`) без свободной команды или предлагаемого значения.
- Администратор с TOTP видит ограниченную очередь, меняет состояние через CAS и reason code. Администратор не утверждает и не завершает собственный запрос. События append-only; SQLite runtime/миграция и PostgreSQL миграция запрещают UPDATE/DELETE событий на уровне DB.
- Legal hold содержит scope `user`, reason code, автора и время создания/снятия. Детали доступны только администратору; активная запись блокирует утверждение удаления. Уникальный индекс допускает один активный hold на пользователя. Если hold установлен после одобрения удаления, это одобрение атомарно возвращается в `in_review` с событием; общая блокировка строки пользователя сериализует оба действия. Dry-run показывает только категории/количества и причины блока, без текстов, контактов или payload.
- При одобрении `restrict` снимается `notify_consent` у поисков этого пользователя и новые согласия отклоняются; установка флага и включение уведомлений используют ту же блокировку строки пользователя. Полный архив не формируется: приватный `export-manifest` сообщает `generator_enabled=false`, `ready=false`, `download_url=null`. Статус `completed` для `access|export|delete|correct` заблокирован до отдельного исполнителя/политики. Никаких публичных ссылок, cron delete и внешних alerts нет.

## Проверка и открытые решения

Адресный API/schema/Alembic/saved-search набор **38 PASS, 2 SKIP** покрывает replay/mismatch, чужой user 404 без изменения, TOTP, stale CAS 409, self-decision, legal hold, запрет завершения удаления, отсутствие заметок/секретов в manifest, реальное отключение необязательных уведомлений, неизменяемость событий, SQLite upgrade/downgrade и opt-in PostgreSQL. Полный локальный API suite **604 PASS, 8 SKIP**; PostgreSQL без `TEST_POSTGRES_DSN` остаётся SKIP. Конкурентный тест двух соединений подтверждает сериализацию блокировки пользователя на SQLite; полный interleaving с PostgreSQL не воспроизводился. Web UI в профиле и `/admin` проверен одним браузерным E2E на временной SQLite (**1 PASS**): создание, приватность, операторское рассмотрение, hold/план/снятие, итоговый статус пользователя, мобильная ширина 390 px и задержанный ответ старой сессии после смены аккаунта. TypeScript, 14 web unit-файлов и build прошли локально. Независимый read-only reviewer после исправлений не нашёл оставшихся конкретных P0/P1/P2.

Остаются: утверждённая policy хранения и прав, сопоставление полного графа FK/cascade и чужих tenant данных, безопасный экспорт с лимитом размера/сроком действия, отдельный исполнитель удаления, поведение общих профилей и медиа, staging/production с реальной БД и AV. До этих решений технический план всегда `blocked=true`.
