# Подтверждение принятия обращения — локальный кандидат

Назначение тикета и его принятие разделены. `assigned_to_user_id` означает,
кому передано обращение; `accepted_by_user_id` и `accepted_at` появляются
только после явного действия «Взять в работу» под 2FA. Передача, снятие
назначения и ручная эскалация сбрасывают принятие. После повторного открытия
назначение сохраняется, но сотрудник подтверждает принятие заново.

Изменение защищено `If-Match`/`state_version`, проверкой роли и объектных
прав. Повторное принятие тем же сотрудником возвращает прежнюю версию;
системный журнал фиксирует отдельное событие принятия. API очереди показывает
назначение и принятие персоналу; пользовательский ответ не раскрывает ID
сотрудника. Интерфейс даёт назначенному сотруднику кнопку подтверждения.

Миграция `a06f78d90e12` после `a05f67c89d01` добавляет nullable поля,
сохраняя исторические назначения как **не подтверждённые**. Проверка пары
полей устанавливается для новой схемы и миграции; manifest остаётся
`draft/manual_block`. Фактические source revision, backup/restore и PostgreSQL
rehearsal необходимы до staging.

Это **не** устанавливает срок принятия срочного обращения: владелец пока
не утвердил его. Автоматическая эскалация, реальные Telegram/email адресаты,
доставка и staging/production остаются открытыми. Локальный срез не закрывает
критерий S06 или P05 повторно; полный запуск остаётся 59,00%.
