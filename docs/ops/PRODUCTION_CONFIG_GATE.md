# Production configuration gate — Букер

API проверяет `BOOKER_RUNTIME_ENV=production` в начале FastAPI lifespan, **до** `init_schema` и seed. Небезопасное значение завершает старт с ошибкой без вывода секрета. Local/test используют только локальный тестовый ключ при отсутствии явного ключа; staging и production требуют собственный `BOOKER_TOTP_ENCRYPTION_KEYS`. Этот gate не включает live acquiring и не заменяет юридический/партнёрский допуск.

## Обязательная конфигурация

Шаблон [systemd](../../infra/systemd/booker-api.service) закрепляет `BOOKER_RUNTIME_ENV=production` в `ExecStart`, задаёт `BOOKER_PAYMENT_PROVIDER=external`, закрытый CORS, обязательную 2FA и `audit` in-app transport без отправки наружу. Это сохраняет прежний журнал уведомлений `dev` без dev-имени в production; `audit` не разрешён для email/SMS/push. Защищённый `/etc/booker/booker-api.env` (root:root, `0600`) должен содержать `BOOKER_DATABASE_URL`, уникальный `BOOKER_WEBHOOK_SECRET` и отдельный Fernet-ключ `BOOKER_TOTP_ENCRYPTION_KEYS`; пример с placeholder в [env.production.example](../../infra/env.production.example) **не готов к запуску**. Создавайте случайные значения в доверенном хранилище секретов, не переносите их в git, лог или чат. Ключ TOTP должен оставаться доступен после перезапуска и восстановления БД.

Production gate принимает `external` или `disabled` payment provider. `stub` и live provider отклоняются: live adapter остаётся заглушкой до отдельного правового, партнёрского и staging gate. `BOOKER_ALLOW_DEFAULT_WEBHOOK_SECRET=false`, `BOOKER_REQUIRE_ADMIN_2FA_ENFORCED=true`, `BOOKER_PUBLIC_URL=https://bukergo.ru`, CORS — только `https://bukergo.ru` и при необходимости `https://www.bukergo.ru`. Localhost, HTTP, wildcard, дополнительные origins, `BOOKER_ALLOW_DEMO_SEED=1` и любой `dev` notification transport запрещены. Отдельного session secret в этом API нет: сессии — случайные непрозрачные токены в БД; `BOOKER_SESSION_SECRET` не поддерживается и в production вызывает отказ, чтобы не создавать ложное ощущение защиты.

## Проверка перед запуском

1. Проверить защищённый env-файл и фактические systemd overrides: `systemctl cat booker-api`, `stat -c '%U:%G %a' /etc/booker/booker-api.env`. Не печатать содержимое env-файла в журнал/чат. Перед остановкой сервисов deploy-скрипт вызывает `infra/preflight_booker_api.py` с новым unit-шаблоном и env-файлом; он не выводит секрет и прекращает deploy при ошибке. Preflight отвергает shell-синтаксис `export`, пустой/относительный DB URL; для текущего SQLite unit требуется `sqlite:////opt/booker/data/booker.db`, либо явный PostgreSQL URL. Прямой `booker_api.seed` отказывает в production даже с `BOOKER_ALLOW_DEMO_SEED=1`.
2. На изолированной копии конфигурации и БД проверить локальные тесты: `cd apps/api && .venv/bin/python -m pytest -q tests/test_production_config.py`; весь API suite — `.venv/bin/python -m pytest -q`. Тесты с `TEST_POSTGRES_DSN` остаются отдельным gate.
3. До остановки работающих сервисов убедиться, что `preflight_booker_api.py <unit-file> <env-file>` под итоговой конфигурацией проходит. Миграция `a04f56b78c90` должна зашифровать все старые TOTP-значения на проверенной копии БД с тем же ключом **до** запуска нового приложения; требуется отдельное ревью `manual_block`, sealed backup и restore. Затем на staging проверить старт, `/health`, вход администратора с TOTP, восстановление кода, внешний путь сделки и отсутствие отправки из dev transports. Не считать успешный health проверкой сделки.
4. При отказе запуска исправить только неверные переменные в защищённом файле/override и повторить staging. Откат приложения — предыдущий проверенный артефакт и конфигурация по [runbook](PROD_INFRA.md); не ослаблять gate и не подставлять default secret ради старта.

В текущем дереве шаблон systemd был изменён локально. Фактический production env, установленный unit и успешный staging/production старт **не проверены**; применять шаблон без заполненного секрета нельзя. Статус: локально проверенная защита запуска, не релизный допуск.
