# Приоритет человеческих обращений из помощника — локальная правка

Проверка текущего маршрута выявила три случая, которые помощник правильно
передавал человеку, но итоговый тикет попадал в `other/normal`:
отмена выступления исполнителем, две подтверждённые брони на один слот и
подозрение на взлом аккаунта. Теперь первые два получают категорию `incident`,
последний — `profile`; все три получают приоритет `high`. Это влияет на
операторскую очередь и адресный сигнал о новом обращении.

Для этих случаев `urgency_code` и `response_due_at` остаются пустыми:
утверждённый SLA определён только для `event_day_no_show` и
`paid_not_confirmed`. Помощник не обещает срок и не принимает решения по
сделке, доступу или компенсации. Прямое ручное обращение с текстом о двойной
броне также получает `high`, сохраняя категорию, которую выбрал пользователь.

Локальная проверка: 62 PASS в наборах triage, помощника и доставки нового
тикета; дополнительные права, мониторинг и регрессии handoff — 32 PASS;
Ruff PASS. Staging, фактический дежурный и внешняя доставка не проверены.
`P05` уже учтён в реестре; готовность полного запуска остаётся 59,00%.

## Явная просьба о человеке сохраняет контекст

Ранее слово «оператор» обрабатывалось до смысловой темы и могло заменить
`account_security` или `money_or_legal` на общий `human_request`. Теперь
помощник сначала определяет проблему, затем добавляет явную передачу человеку.
Для чистой просьбы без описания проблемы остаётся `human_request`. При
передаче известные темы получают предметные категории: доставка кода,
приглашение и профиль поставщика — `profile`; доступ к документу —
`technical`; неопределённое неприбытие — `incident`. Это меняет
маршрутизацию тикета, но не даёт помощнику полномочий менять сделку.

После дополнения адресный API-набор с регрессиями поддержки и прав —
85 PASS. Браузерный сценарий с фразой «возврат оплаты, нужен оператор» —
1 PASS на временной SQLite; в нём проверены `money_or_legal` и категория
созданного тикета `payment`.

## Резервные коды сотрудника в обращении

Локально воспроизвели сохранение резервного кода восстановления TOTP,
вставленного без метки, в тексте помощника или ручного тикета. Фильтр перед
записью теперь скрывает формат из шести групп по четыре шестнадцатеричных
символа и компактную форму из 24 символов. Регрессия проверяет ответ API,
обмен помощника, тикет и сообщение оператору; это не очистка старых записей.

При сообщении о потере Authenticator помощник объясняет только существующий
путь оператора или единственного администратора с сохранённым кодом. Если
кода нет или администраторов несколько, предлагает передачу человеку;
тикет получает категорию `profile` и приоритет `high` без нового SLA.
Почта сама по себе не восстанавливает административный доступ. Адресные
API-наборы по помощнику, маршрутизации и безопасности — **85 PASS**;
Ruff и `git diff --check` — PASS. Это локальная правка; staging,
production и реальная процедура нескольких администраторов не проверены.
`P05` уже учтён, готовность полного запуска остаётся 59,00%.

Чтение ранее сохранённых записей теперь также скрывает распознанный код
в ответах истории помощника и тикета. При новой передаче старой сессии
оператору текст очищается перед записью нового тикета. Локальная регрессия
создаёт старую строку с кодом и проверяет оба API и сохранённый новый тикет;
адресный набор после дополнения — **86 PASS**. Исходная старая строка в БД
и резервных копиях этим не исправляется: для очистки данных на выбранной БД
нужны инвентаризация, backup/restore и отдельная процедура с аудитом.
