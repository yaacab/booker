# Исторические секреты поддержки: scoped maintenance

`booker_api.support_secret_backfill` удаляет распознаваемые секреты только из записей поддержки **одной организации** или из личных записей **одного пользователя без организации**. Скрипт не является поиском всех видов секретов и не заменяет ротацию раскрытого ключа. Production-запуск в этом транше не выполнялся.

## Область изменений

Allowlist: `support_tickets.subject/body/request_fingerprint`, `support_messages.body/request_fingerprint`, `support_operator_notes.body/request_fingerprint`, `support_agent_exchanges.user_message/assistant_message/request_fingerprint`, `support_agent_feedback.comment`. Эскалация копирует текст помощника в тикет и его первое сообщение; обе копии входят в выбранную tenant-область. Тикетный fingerprint ручного обращения пересчитывается из очищенных полей, а nullable fingerprint тикета эскалации очищается, поскольку исходный `reason_code` из digest восстановить нельзя. Idempotency key hashes, статус, участники, связи, даты и аудит не изменяются. Generic email outbox не включён: текущий код поддержки не создаёт там письма, но это не доказывает отсутствие исторических внешних копий.

Отчёт содержит версию формата, тип scope, счётчики строк/полей, копий эскалации и расхождений между тикетом и первым сообщением, а также непрозрачный `plan_token` (HMAC по точному плану изменений). В нём нет текста, идентификаторов строк, исходных fingerprint или URL БД. Несовместимая связь тикета/сессии разных scope прерывает запуск. При `copy_mismatches_after_sanitization > 0` apply блокируется: сначала требуется ручная сверка, поскольку скрипт не заменяет одну копию другой. Вызов требует новой сессии БД без незавершённой транзакции.

## Порядок для отдельного контура

1. Сделать защищённую резервную копию и остановить запись API в выбранные support-таблицы. Для Postgres выполнять maintenance отдельно от пользовательского трафика; конкурентный сценарий на PostgreSQL не проверен.
2. Подать `BOOKER_DATABASE_URL` и постоянный для данного dry-run/apply секрет `BOOKER_SUPPORT_BACKFILL_PLAN_KEY` (минимум 32 байта) через защищённое окружение, без строки подключения или ключа в командной строке. Не публиковать ключ в отчёте. Убедиться, что выбран нужный контур.
3. Сначала dry-run:

   ```bash
   cd /home/art67/booker/apps/api
   .venv/bin/python -m booker_api.support_secret_backfill --organization-id ORG_UUID
   ```

   Для личных обращений без организации использовать `--unscoped-user-id USER_UUID`; оба scope одновременно запрещены. Общего режима `all tenants` нет.
4. Сверить счётчики. Если `copy_mismatches_after_sanitization` ненулевой, установить причину до apply. Применить ровно к тому же scope с `changed_fields` и `plan_token` из свежего dry-run:

   ```bash
   .venv/bin/python -m booker_api.support_secret_backfill --organization-id ORG_UUID --apply --expected-changes N --plan-token PLAN_TOKEN
   ```

   При несовпадении числа изменений, токена точного плана или при расхождении копий apply отклоняется без записи. Вся область одного запуска коммитится одной транзакцией. Повторный dry-run должен вернуть `changed_fields: 0`.
5. Отдельно проверить доступность тикета и повтор старого idempotency key через API. Ротировать раскрытые ключи и решить судьбу старых резервных копий/логов по политике хранения. Сам скрипт не удаляет внешние копии и не рассылает уведомления.

Проверено только на временной SQLite в API-тестах. Скрипт не запускает миграции схемы и не требует/не выполняет deploy. Текущая реализация обрабатывает весь один tenant scope одной транзакцией; объёмные tenant-области требуют отдельного batch/нагрузочного испытания перед применением.
