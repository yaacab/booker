# Общий rate limit: локальный срез 02.10.2026

До среза все счётчики находились в `rate_limit.py` в памяти каждого worker. Новый режим `auto` использует БД в staging/production; local/test сохраняют изолированный in-memory режим. Production отвергает явный `BOOKER_RATE_LIMIT_BACKEND=memory`. Это исходный код и локальные тесты, а не проверка установленного сервера.

## Точки вызова и политика

| Группа | Текущее покрытие | При отказе хранилища |
|---|---|---|
| Регистрация, login, recovery и confirm | 20 / 5 мин на доверенный IP и отдельный route scope | 503 до изменения состояния |
| Admin TOTP | Логин и проверка fresh TOTP / заголовка: общий лимит 30 / 5 мин на user без IP; смена сети не даёт новый счётчик. Часть admin mutation также имеет 10 / 5 мин per-action | 503 до проверки кода и мутации |
| Webhook | 120 / мин на IP до обработки события | 503, провайдер может повторить доставку |
| Вложения сделки | 30 / 5 мин на IP до сохранения файла | 503 |
| Сообщения | 60 / мин: заявки, Deal Room, support и operator reply; отдельные префиксы или user scope | 503 |
| Создание заявок | 20 / час: quick request, запрос события, публикация брифа и отклик; обязательный user+org scope там, где org известен, без IP, чтобы смена сети не сбрасывала лимит | 503 до создания |
| Claim площадки | 5 / час на user+org после проверки членства; смена IP не сбрасывает лимит | 503 до записи |
| Support-сессии и тикеты | Отдельные лимиты 5 / 10 мин и 10 / час | 503 |
| Analytics и promo | 120 / мин на IP | Явный fail-open; отказ не меняет коммерческое состояние |

Не все маршруты покрыты отдельным лимитом: создание события, часть административных действий без fresh TOTP (включая verification/dispute intake и outbox retry), чтение каталога и остальные CRUD. Там остаются авторизация, проверка прав и обычные бизнес-инварианты, но per-route anti-abuse не доказан. Нужен отдельный адресный аудит нагрузки и лимитов без поломки легитимных массовых операций.

## Хранилище и границы

Счётчик — фиксированное окно по времени БД. Один `INSERT ... ON CONFLICT DO UPDATE ... WHERE hits < limit RETURNING` атомарно допускает не более `N` запросов на один ключ и окно между процессами; 429 содержит `Retry-After`. По умолчанию production SQLite использует соседний файл `<booker.db>.rate-limit` и не берёт write lock бизнес-транзакции. На PostgreSQL таблица `rate_limit_counters` создаётся Alembic-ревизией `fa6d7e8f901b` в общей БД. SQLite-решение разделяет лимит только между процессами **одного хоста**; для нескольких API-хостов нужна общая PostgreSQL. Реальный PostgreSQL и VPS не проверялись.

В БД сохраняются только HMAC-SHA256 ключа и номера окна, время истечения и счётчик. HMAC использует production webhook secret; все API экземпляры должны иметь одинаковый секрет. Его ротация начинает новое окно счётчиков. Каждый 64-й вызов удаляет до 256 завершившихся окон отдельной транзакцией; при полном простое очистка не запускается. Таблица не содержит сырой IP, user ID, токены или TOTP.

`X-Real-IP` принимается только при прямом TCP peer из `BOOKER_TRUSTED_PROXY_CIDRS` (по умолчанию loopback) и только как один валидный IP. Production unit запускает Uvicorn с `--no-proxy-headers`, чтобы peer не был переписан из клиентского `X-Forwarded-For`; preflight требует этот флаг. Nginx задаёт `X-Real-IP` из `$remote_addr`. Для другого proxy topology CIDR и ingress-конфигурацию нужно отдельно проверить, включая spoofing извне.

## Проверка и выпуск

Тесты `test_rate_limit_shared.py` покрывают два FastAPI instance, два процесса, конкурентный доступ, restart, scopes, 429/Retry-After, истечение, cleanup и отказ backend без создания аккаунта. `test_rate_limit_regression.py` проверяет недоверенный и доверенный proxy; Alembic-тесты — миграцию и URL PostgreSQL с паролем/`%`. `test_rate_limit_postgres.py` запускает конкурентный тест в изолированной схеме только при `TEST_POSTGRES_DSN`; в этом срезе он пропущен, потому что DSN отсутствует. Локальные результаты и оставшиеся проверки зафиксированы в [completion audit](COMPLETION_AUDIT_2026-10-01.md).

Перед выпуском нужны PostgreSQL concurrent test на отдельной схеме, проверка фактического production unit/proxy, прав доступа к файлу SQLite, наблюдение за 429/503 и реальный многоworker smoke. При откате код/юнит возвращаются вместе, а добавочная таблица и SQLite-файл могут оставаться как данные счётчиков; удалять их во время трафика нельзя. Deploy, commit и push в этом срезе не выполнялись.
