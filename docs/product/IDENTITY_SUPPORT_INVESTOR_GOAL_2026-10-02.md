## 2. Целевая архитектура без второго пользовательского мира

**Один `users.id`; способы входа отделены.** Сохранить существующие ID, организации, юридические события и сессии. Добавить `user_identities` с уникальным `(provider, provider_subject)` для `telegram`, `yandex`, `vk` и ссылкой на `users.id`; фиксировать адрес/телефон провайдера только при полученном разрешении, `linked_at`, `last_login_at`, происхождение и состояние проверки. Email провайдера не даёт права автоматически объединить пользователей. Совпадение с существующим email означает вход старым способом и явную привязку с повторным подтверждением. Перед отвязкой сервер проверяет, что остаётся хотя бы один **работающий** способ входа. Организационные роли заказчика/исполнителя/площадки остаются в `Organization`/`TeamMember`; `operator` и `admin` нельзя выбрать публично.

**Совместимость схемы.** На этапе A сначала ввести таблицу привязок и инвентаризировать обращения к обязательным `users.email`/`password_hash`. Отдельной проверенной миграцией разрешить отсутствие локального email и пароля для внешнего аккаунта; без фиктивного адреса, пароля или ложной метки `email_verified_at`. Устаревшие сессии переводить с наблюдаемой миграцией/сроком, не разлогинивать пользователей неожиданно. Миграция должна иметь конкретный source revision, sealed backup текущего engine, restore, план обратного переключения кода и ручной review `schema-release-manifest` до staging.

**Первый фактор.** Telegram Mini App принимает только сервером проверенный `initData` с ограничением времени и защитой от повтора, связывает `Telegram user_id` с `users.id` и выдаёт Booker-сессию без повторного логина после подтверждения Telegram. До включения проверить, существует ли Mini App вне этого репозитория: в текущем Booker его backend/frontend не найден. Яндекс ID — серверный authorization-code callback, минимальный scope, `state`, фиксированный Redirect URI, хранение client secret только в secret storage. VK ID — текущий VK ID OAuth 2.1/PKCE, `state` и server-side callback; точные endpoint и scope сверить с документацией перед кодом. OAuth-токены не писать в localStorage, URL страницы после callback, audit и логи. Яндекс/VK — только первый фактор: operator/admin после них всё равно проходят Booker TOTP.

**Booker 2FA.** В `Профиль → Безопасность` дать добровольные SMS и стандартный TOTP для обычных ролей. Номер сперва подтверждается; SMS: шесть цифр, TTL около 5 минут, одноразовое проверяемое представление, 5 попыток, resend не чаще 60 секунд, cooldown и лимит по аккаунту/IP/устройству. SMS-провайдер — интерфейс с выключенным режимом до реального транспорта и E2E. TOTP включается только после верного кода нового секрета; затем секрет хранится зашифрованным с доступом auth subsystem. Миграция старого admin/operator секрета должна сохранить возможность входа и не печатать значения. Recovery kit: 10 одноразовых кодов, однократный показ, только безопасные хеши в БД, ротация уничтожает старые коды и требует step-up. Для operator/admin TOTP обязателен; SMS не единственный административный recovery-фактор.

**Восстановление.** У пользователя: одноразовый recovery code → проверенный резервный фактор → отдельно утверждённая процедура. У оператора: recovery code или админская проверка личности с immutable audit и обязательным новым TOTP при входе. У администратора: два независимых уполномоченных подтверждения при нескольких админах; для единственного — заранее сохранённый offline recovery kit. Email сам по себе не снимает TOTP. Нужны правила полномочий, независимых доказательств, уведомлений, охлаждения и экстренного пути, утверждённые владельцем до реализации чувствительного endpoint. После восстановления отозвать прочие сессии и прежние факторы.

**Сессии и step-up.** Показывать устройство, браузер, ОС, приблизительную IP/географическую информацию, способ и время входа/активности; дать отзыв одной/всех остальных сессий. Повторное подтверждение для смены email/телефона, 2FA, recovery codes, linking/unlinking, реквизитов, ролей, крупных возвратов и критического admin-действия. Уведомлять о новом устройстве, изменении идентичности/ролей/факторов, recovery и админской сессии. Журнал: actor, subject, событие, UTC, IP, session/device, correlation ID, разрешённые before/after; обычный оператор не может изменять историю. Не сохранять сырые OTP/токены/коды или избыточный профиль устройства.

Маршрут `primary Павел → backup (не назначен) → administrator`; до назначения backup срочное непринятое за SLA и просроченное обращение автоматически эскалируются admin. ## 5. Инвесторский показ — отдельная приёмка

Подготовить изолированное staging/демо с правдивыми тестовыми профилями и понятным бейджем `Демонстрация`; сценарий 10–12 минут: поиск → создание события → заявка/чат → оффер и серверная цена → hold/договор как технический черновик → **симуляция/external без заявления об оплате банком** → кабинеты сторон → операторская поддержка/эскалация. Каждое основное действие действительно переходит в следующее состояние в тестовом контуре; пустые кнопки, фальшивые успехи и выдуманные партнёры не принимаются. Отдельно показать, какие пути находятся за legal/payment gate. Проверить 390/1440, ошибки/пустые состояния, клавиатуру и доступность.

Сверить `docs/investors/DEMO_SCRIPT.md` с фактическими маршрутами: `/investor/venues` сейчас закрыт и содержит исследовательские записи, `/deals/demo` лишь перенаправляет. Нельзя выдавать исследовательские 300 площадок за подтверждённых партнёров или их фотографии за разрешённые. Финальный визуал и конкретная анимация «Рамка слота» проходят отдельное утверждение владельца **до** переноса в рабочий frontend. Метрики питча должны иметь источник и дату; seed-данные не являются traction.

## 6. Внешние решения и секреты

Владельцу нужны: способ read-only доступа к действующей БД или проверенный администратором вывод по Павлу; точный staging URL/engine/revision; Pavel user/email и действительные рабочие адресаты Telegram/email; выбор SMS-провайдера и отдельные приложения Яндекс ID/VK ID для staging и production; утверждённый offline/двухлицевой admin recovery; согласование демонстрационного сценария и финального motion. Ни один ключ не присылать в обычный чат.

Для Яндекс создать **приложение для авторизации пользователей**, указать web Redirect URI каждого окружения и минимальные данные. Официальная документация: <https://yandex.ru/dev/id/doc/ru/register-auth>, <https://yandex.ru/dev/id/doc/ru/codes/code-url>. Для VK использовать современный VK ID SDK/OAuth 2.1; конкретные endpoint/scopes/PKCE сверить при этапе C: <https://github.com/VKCOM/vkid-web-sdk/blob/master/README.md>. Client secret и токены — только backend/secret storage. Callback URL задавать после выбора подтверждённого staging-домена.

НПД, юридическая форма оператора, карта денег/чеков, прямая договорная роль, ЮKassa и пилотные поставщики остаются внешними решениями из `docs/legal/NEXT_CHAT_SERVICE_LEGAL_HANDOFF.md`: письменное заключение юриста/бухгалтера и ответ партнёра до live денег. Комиссия и `quote_id` фиксируются сервером в версии оффера; для пилота выбрать одно правило тарифа, а не диапазон в клиенте. Персональные данные и медиа публиковать только при подтверждённом основании, сроках хранения, правах и server-side eligibility. Никаких реальных уведомлений, публикации документов или платежей из этого плана автоматически не следует.

Перед денежным сценарием подготовить для юриста, бухгалтера и ЮKassa одну схему: стороны и роли; заказчик → аванс/остаток/обеспечение; комиссия Букера; отмена/частичный и полный возврат; выплата исполнителю и площадке; получатель каждой суммы и лицо, выдающее чек. Отдельно проверить совместимость НПД с фактической агентской/посреднической моделью.
