# Букер — текущая цель разработки

**Решение владельца: 02.10.2026.** Текущая очередь — технический MVP в репозитории `booker`. Полное продуктовое видение и инварианты остаются в [CONTRACT.md](product/CONTRACT.md). [PROJECT_PROGRESS.md](PROJECT_PROGRESS.md) отдельно считает технический MVP, красивый сайт с дизайном и полный запуск; текущая очередь не закрывает критерии двух других результатов и не даёт допуска к работе с клиентскими деньгами или production.

## Результат текущей очереди

Проверенный на точном SHA технический путь: каталог и достоверная доступность → профиль → событие/заявка → переписка → версия предложения → hold/бронь в тестовом контуре → кабинеты сторон → операторская поддержка. Сервер проверяет права на каждом объекте, предотвращает двойное бронирование и ведёт аудит переходов. Мобильный браузер и отрицательные сценарии проходят на staging с тестовыми данными. Результат называется **техническим MVP**, а не запущенной коммерческой сделкой.

## В этой очереди

1. Сохранить и проверить существующие продуктовые вертикали; исправлять подтверждённые дефекты доступа, календаря, переписки, версий предложения, hold, кабинетов и поддержки.
2. Закрыть технический путь восстановления доступа администратора и проверить реальную доставку почты; проверить изоляцию организаций, вложения и доступность на мобильном устройстве.
3. Измерить каталог на представительном наборе данных; воспроизвести миграции и восстановление **выбранной фактической БД** на staging вместе с uploads; проверить конфигурацию, мониторинг и откат.
4. Собрать точный кандидат из обозримых коммитов; прогнать полный API, web, browser и security CI на этом SHA; выполнить авторизованный staging E2E без настоящих денег.

## Отложено до отдельного решения

- Юридическое утверждение и публикация документов, договорный/подписной контур для реальных сделок, расчёты с партнёром и финансовая модель.
- Подключение live-эквайринга, capture, refund, payout и любые реальные денежные сценарии. Существующий код и его защитные тесты сохраняются; новые функции здесь не развиваем в этой очереди. Тестовые `stub`/`external` статусы не выдаются за подтверждённый платёж.
- Новый визуальный дизайн, Figma и motion разрабатываются **отдельным проектом**; в `booker` сейчас только необходимые функциональные, доступные и адаптивные исправления. Перенос утверждённого дизайна — отдельная будущая интеграция.
- Production-релиз, коммерческий пилот и заявление о готовности для клиентов.

## Рабочий цикл

1. Перед задачей сверить `git status`, владельцев пересекающихся файлов, `CONTRACT.md` и затрагиваемый критерий. Текущее большое dirty дерево не очищать и не коммитить целиком.
2. Брать одну завершённую вертикаль или дефект с ясным результатом. Сначала узкая проверка, затем полный набор затронутого приложения и `git diff --check`. Миграция, код и проверяющий её тест должны оставаться в одном логическом срезе.
3. Посмотреть точный staged diff, проверить отсутствие секретов и временных файлов, создать содержательный коммит. Не использовать массовый `git add -A`.
4. Для GitHub CI нужен PR к `main`/`master`: текущий workflow не запускается от push в feature-ветку. Отправлять проверенный срез в текущую рабочую ветку и открыть/обновить обозримый PR; пока CI идёт, делать независимую работу. Потом проверить результат на том же SHA и исправить конкретные сбои.
5. После значимого среза обновить [PROJECT_STATE.md](PROJECT_STATE.md): состав, SHA, тесты, уровень доказательства и открытые риски. Три шкалы [PROJECT_PROGRESS.md](PROJECT_PROGRESS.md) менять только при выполнении их исходных критериев; показывать изменение и остаток отдельно. Staging, production и внешние решения не заменяются локальными тестами.

**Первый практический шаг:** разложить текущее dirty дерево по связанным частям и выделить проверяемый кандидат для S06 и технических P08/O04; затем перейти к staging E2E и восстановлению БД. Точное состояние кода и документации проверять заново перед каждым срезом.
